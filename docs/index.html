      System design

      An @mention is a distributed system with a three-second front door.

      Everything here exists because the chat platform retries any event it thinks you dropped, using the same event id. Split at that deadline and the rest follows: what you can no longer do synchronously has to become a queue, and what a queue makes possible is a team of agents rather than one prompt.

      How to read these diagrams

      Every diagram uses the same three shapes, so what exists and what is proposed can be told apart at a glance rather than from a caption.

      Data flow

      One mention, end to end. Everything below ack happens after the platform has already been told 200 OK.

      Three tiers, not one pipeline

      A prior review of this repo collapsed nine nodes to five and deleted the planner/critic split, on the grounds that it hand-rolls the model's own loop with worse adaptivity. That finding is not reversed here — it is the default. Debate is the escalation, and it engages only where the mechanical verifier is structurally blind.

      The trigger conditions are the exact complement of what the verifier can check.

      The verifier checks tokens, so it is blind to causation — therefore a causal question escalates. The verifier checks what is said, never what is done, so it is blind to writes — therefore a non-auto tool escalates. That is a boundary, not a heuristic, and it is why the predicate is code rather than a model call.

      The roster

      Each agent owns exactly one decision. Open any card for the full system prompt it is sent — these are the same strings the simulator assembles, read from the same array, because the previous version of this page documented one roster while animating another.

      The debate protocol

      A debate with no termination proof is a bug, and a critic that sees what the planner saw is the rubber stamp this design already deleted once.

      The verifier

      The one place a second model was replaced by forty-five lines of code, because a model reading the same context inherits the first one's misreadings.

      It advertises its own biggest hole.

      Right tokens, wrong relationship: if the evidence says 41/s at 15:01 and the draft says 41/s at 14:01, both tokens are present and the pairing is invented. That passes. Fixing it needs span-level evidence binding, which is not forty-five lines. A verifier that claims completeness is the falsely-verified-code failure this repo has already hit four times.

      Memory

      The part that is a security boundary rather than a feature.

      The scope filter belongs in the query predicate, never after retrieval.

      Post-filtering leaks through result counts, ranking behaviour and latency, and it sits one refactor away from being deleted by someone who reads it as a redundant guard. Scope is derived from the inbound event's channel binding — never from anything in the request body, because in a public channel the request body is attacker-controlled. Run the Scope boundary flow: the excluded count is shown, and the hits are absent from the result set rather than removed from it.

      The MCP catalogue

      This is the live table the simulator dispatches against. A schema or clamp you can read here is one that actually rejects when you run a flow.

      There is no slack.post_message, and that is the most important row in the table.

      Posting is a graph edge that runs after the verifier and is fenced by db.reserve_post(). As a tool it would hand the agent a path around the verifier, and a gate that can be bypassed is not a gate. tools/check_registry.js fails the build if the tool ever appears — along with any irreversible write whose policy is auto.
